# tools.py修改说明：架构第二层与第三层修改说明

本次代码的核心修改集中在第二层和第三层。

整体目标是把原来“LLM 直接判断标题等级”的方式，改成更加稳定的两步结构：

```text
第二层：恢复完整、独立的目录标题
第三层：重建标题父子关系，并由程序计算最终等级
```

也就是说，系统不再主要依赖 LLM 直接输出 `H2 / H3 / H4 / H5`，而是先保证目录标题本身正确，再根据标题之间的父子关系确定最终 Markdown 等级。

## 一、第二层修改说明

第二层的职责仍然是解析第一层确认出来的目录区域，输出目录标题列表。

旧版第二层的处理方式是：

```text
目录原文
→ 清洗目录行
→ 交给 LLM
→ LLM 同时完成标题提取、断行合并、等级分配
→ 输出 toc_headings
```

这种方式的问题是，LLM 在同一步里需要同时完成三个任务：

```text
判断哪些行是标题
判断哪些行应该合并
判断标题等级是多少
```

在普通目录中可以工作，但在复杂目录中容易出错。典型问题包括：

```text
OCR 断行标题被错误拆开
无编号并列标题被错误合并
英文目录中的无编号子标题被误判为续行
实验 / 项目章节中的固定栏目污染目录树
章节等级出现逐渐下沉
```

新版第二层的核心变化是：

```text
先恢复逻辑标题，再进行初始等级判断。
```

它不再简单把目录中的每一行都当成独立标题，而是先判断目录行之间的真实关系。

例如：

```text
第18章 虚拟化云计算平台
Proxmox VE
```

这属于 OCR 或版式导致的断行，应该恢复为一个完整标题：

```text
第18章 虚拟化云计算平台 Proxmox VE
```

但下面这种情况不能合并：

```text
2.3 Tokenization and LLM capabilities
LLMs are bad at word games
LLMs are challenged by mathematics
LLMs and language equity
```

这里后三个无编号标题是 `2.3` 下面的并列子标题，不是 `2.3` 的标题续行，所以应该作为独立标题保留。

因此，新版第二层更强调“标题原子性”。

第二层现在主要解决的问题是：

```text
标题是否完整
标题是否独立
标题是否被错误合并
标题是否被错误拆分
目录中哪些内容不是正式标题
```

最终，第二层输出的重点不是最终等级，而是一个更加干净、稳定的目录标题列表：

```json
[
  {"text": "第1章 Linux基础", "level": 2},
  {"text": "1.1 Linux简介", "level": 3},
  {"text": "Linux的特点", "level": 4}
]
```

这里的 `level` 更像是初始参考等级，不再是整个系统最终依赖的唯一判断结果。

## 二、第三层修改说明

第三层是本次结构变化最大的部分。

旧版第三层主要是“规则校验标题等级”。

它会根据标题编号和经验规则修正第二层输出的等级，例如：

```text
第1章 / 第2章 → H2
1.1 / 2.3 → H3
1.1.1 / 2.3.4 → H4
无编号标题根据前后标题局部判断
```

旧版第三层的处理方式可以概括为：

```text
第二层输出 text + level
→ 根据编号深度修正等级
→ 根据结构规则修复跳级
→ 根据局部语义修复无编号标题
→ 输出最终等级
```

这种方式的问题是：它仍然围绕 `level` 做修补。

如果第二层把某个标题等级判断错了，第三层只能根据规则局部调整，很难真正理解这个标题到底属于哪个父标题。

新版第三层的核心变化是：

```text
不再让 LLM 直接判断最终 H 等级，而是让 LLM 判断 parent_index。
```

也就是说，第三层要回答的问题从：

```text
这个标题是 H3 还是 H4？
```

变成：

```text
这个标题的直接父标题是谁？
```

例如：

```text
9.2 Design stage
Development stage
```

旧方式可能让 LLM 直接判断：

```text
Development stage = H5
```

新版方式改为让 LLM 判断：

```text
Development stage.parent_index = 9.2 Design stage
```

然后程序再根据父子关系确定等级：

```text
9.2 Design stage 是 H4
Development stage 是它的直接子标题
所以 Development stage = H5
```

这样做的关键好处是：标题等级不再由 LLM 直接决定，而是由程序根据目录树深度确定性计算。

## 三、为什么第三层改为 parent_index

标题等级本质上不是标题自身的孤立属性，而是标题在目录树中的相对位置。

例如：

```text
Summary
```

它可能是：

```text
全书总结 → H2
章总结 → H3
小节总结 → H4
```

只看标题文本本身，很难稳定判断等级。

但如果知道它的父标题是谁，等级就可以自然推出。

因此，新版第三层把任务拆成两部分：

```text
LLM 负责语义判断：这个标题属于谁？
程序负责结构计算：这个标题应该是几级？
```

这比让 LLM 直接输出 `level` 更稳定。

## 四、第二层和第三层的新分工

修改后，第二层和第三层的分工更加清晰。

第二层负责：

```text
从目录原文中恢复完整标题
识别 OCR 断行
保留无编号并列标题
删除明显不是目录树节点的固定栏目或噪声
输出顺序正确的标题列表
```

第三层负责：

```text
基于完整 Part / Chapter 上下文理解标题关系
判断每个标题的 parent_index
检查 parent_index 是否合法
构建目录树
根据父节点深度计算最终 Markdown 等级
```

整体流程变成：

```text
目录原文
→ 第二层恢复逻辑标题列表
→ 第三层判断 parent_index
→ 程序验证父子关系
→ 程序计算最终 H 等级
→ 输出稳定目录树
```

## 五、修改前后对比

旧版方式：

```text
目录原文
→ LLM 直接输出 text + level
→ 规则修正 level
→ 得到最终标题等级
```

新版方式：

```text
目录原文
→ 第二层恢复完整、独立的逻辑标题
→ 第三层让 LLM 判断 parent_index
→ 程序校验 parent_index
→ 程序根据目录树深度计算 level
→ 得到最终标题等级
```

本质区别是：

```text
旧版：标题 → H等级
新版：标题 → 父标题 → 目录树 → H等级
```

旧版更像是一个黑箱分类任务。

新版更像是一个可解释的结构重建任务。

## 六、修改后的效果

本次修改主要提升以下几类场景的稳定性：

```text
英文目录中大量无编号子标题
OCR 导致标题断行
目录中标题被错误拼接
章节标题等级逐渐下沉
同级标题被误判成父子标题
实验 / 项目章节中的固定栏目干扰目录树
长目录分块后上下文不足导致等级不一致
```

尤其是无编号标题场景，新版第三层可以通过 `parent_index` 判断多个标题是否属于同一个父标题。

例如：

```text
2.2 Data preparation
Loading data
Cleaning data
Validating data
2.3 Model training
```

新版第三层可以判断：

```text
Loading data.parent_index = 2.2 Data preparation
Cleaning data.parent_index = 2.2 Data preparation
Validating data.parent_index = 2.2 Data preparation
```

程序据此可以自动确定：

```text
Loading data
Cleaning data
Validating data
```

三者是同级标题，而不是逐级下沉的父子标题。

## 七、总结

本次代码修改的核心不是简单增加规则，而是改变了标题等级判断的架构。

第二层从：

```text
直接解析目录并返回最终等级
```

调整为：

```text
恢复完整、独立、干净的目录标题原子列表
```

第三层从：

```text
规则修正标题等级
```

调整为：

```text
基于完整语义块重建 parent tree，并由程序计算最终等级
```

最终系统从：

```text
LLM 直接判断 H 等级
```

变成：

```text
LLM 判断父子关系
程序计算标题等级
```

这样可以减少 LLM 在 Markdown 等级数字上的不稳定，把语义判断和结构计算分离，使长文档标题标准化结果更加稳定、可解释、可校验。
